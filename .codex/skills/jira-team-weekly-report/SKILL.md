# Team weekly report

When asked for a weekly report, first run `python3 utilities/clone_weekly_pages.py --yes` from the scripts root to create or reuse the weekly pages for all five projects. The user’s request to create the report authorizes this step. Stop if cloning fails. Then run `python3 .codex/skills/jira-team-weekly-report/scripts/_export_pyffe_jira_weekly.py -o <json-path>` from the scripts root, then read the JSON and write the report in English to a Markdown file. Use the user-specified path if provided; otherwise write `report/jira-team-weekly-report/jira-team-weekly-report-YYYY-MM-DD.md` under the scripts root, where the date is the Monday at the start of the reporting period; create the directory if needed. Return a link to the file. The script requires `requests` and Jira settings in the scripts root `.env` file or environment variables; do not print credentials. The JSON contains internal ticket content and comments: use a temporary file for the raw JSON unless the user requests a saved copy; do not publish the raw JSON.

Report the previous calendar week, Monday through Sunday. The script filters by the current assignee in the configured list or the Jira account running it; do not assume it captures all team activity if tickets changed assignee. It searches for tickets updated since the start of last week, including those updated again afterward, and filters their history and comments to the reporting week. Jira permissions may limit results; descriptions and issue fields reflect their current state, which may differ from the reporting week.

Group work by topic, product, or version. Identify outcomes completed during the week when supported by history or resolution date, and distinguish these from ongoing work. Summarize blockers only when supported by evidence. Group sub-tasks under their parent where appropriate to avoid double-counting, and link relevant tickets as evidence. State when evidence is insufficient. Include the date range, completed work, notable ongoing activity, problems or blockers, and relevant data limitations; omit empty sections. Do not organize the report by individual unless requested. 

After the narrative, include a list of all Jira tickets cited in the report, with each ticket key linked to Jira, its summary, current status, and current assignee display name. Label status and assignee as current because they may have changed since the reporting period. Sort the list by assignee display name (case-insensitively), then by ticket key; place unassigned tickets last and label them Unassigned. Do not expose account IDs. This reference list does not change the team-wide organization of the report.

Start the report with a single Markdown heading containing the report title and date range. Follow it with a top-level Summary bullet and nested bullets for the summary. Use top-level bullets for the remaining section labels and nested bullets for their content; keep the referenced-ticket table nested under its section bullet. Do not use additional headings.

Keep the narrative concise: use a short summary and brief, outcome-focused bullets, combining related work and avoiding repeated details. Preserve essential evidence, blockers, and data limitations.

## Confluence publication

After writing the Markdown report, publish it to the Pyffe weekly Confluence page when the user requests a weekly report. Run `python3 .codex/skills/jira-team-weekly-report/scripts/_publish_pyffe_weekly.py <markdown-path> --start YYYY-MM-DD`, using the Monday from the JSON period. The helper reuses the template and title logic from `utilities/clone_weekly_pages.py` and requires `CONFLUENCE_EMAIL` and `CONFLUENCE_TOKEN`. The publisher excludes the Referenced Jira tickets and Scope and limitations sections from Confluence while retaining them in the Markdown report. It fills the empty Android section of the SAFENEST page cloned in the first step; if that page is missing, it creates it from the template. It stops rather than overwrite an existing Android section; report that result and do not bypass the check. Keep all other sections intact. Return both the Confluence page URL and Markdown file link. The template’s Jira Tickets view is copied as-is and may contain old dates; do not claim it reflects this week.

Prefix each completed or ongoing work bullet with `[DONE]` or `[IN PROGRESS]`, respectively, based on evidence from the reporting week. Do not add a status to summaries, blockers, or items with uncertain status. The publisher converts these markers into Confluence Status macros; retain the markers in Markdown.
